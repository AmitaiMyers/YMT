System design options for the YMT web app

The YMT app (lead research, CRM pipeline, client service hub, and the installable app for phone and desktop) is built and running. This brief shows how the whole system fits together, then three ways to run it in production, cheap, medium and expensive, each with an architecture diagram, how data moves, how it is protected and backed up, and what it costs.

Option 1 · Cheap: single container on Render

Recommended to start

The whole app runs as one container on Render, a managed hosting service that builds it straight from GitHub. The database is a single file (SQLite) on a small permanent disk next to it. This is exactly how the repository is set up today.

How it works

  1. Render receives the request over HTTPS and passes it to the container.
  2. The server checks the session cookie, runs the business rules and reads or writes the SQLite file.
  3. Every push to GitHub rebuilds and restarts the container (under a minute of downtime).
  4. Admins use Settings → Data & Privacy → Download backup to keep a full copy off the server.

Persistent disk 1 GB ($0.25/GB)$0.25
HTTPS + …onrender.com address$0

Total≈ $7.25

Render's free plan cannot be used: it has no disk, so every restart would erase the data.

Strengths

  • No servers to manage, and no code changes.
  • Data in one place in the EU, visible on the app's Data & Privacy page.
  • All security built into the app is active: hashed passwords, secure cookies, audit log, human approval of every message.

Limits

  • Backups depend on someone clicking Download backup.
  • One small machine: comfortable for about 10 users.
  • Disk or region failure = restore from the last downloaded backup.
  • Updates cause under a minute of downtime.
Best for: the pilot, partner demos and the first months with up to about 10 users.

Option 2 · Medium: Render, hardened

Next step

The same single-container design as Option 1, with the weak points closed: more capacity, a company domain, automatic daily encrypted backups to separate EU storage, outage alerts, and a person responsible for it. Upgrading keeps the same data.

How it works

  1. Users open the company address; DNS points it to Render, which handles HTTPS.
  2. The container runs exactly as in Option 1, with 4× the memory.
  3. Every night a backup job makes a consistent copy of the database, encrypts it and uploads it to EU storage at another company. 30 versions are kept.
  4. An uptime monitor calls /api/health; if it fails, the founder and the freelancer get an alert.

Strengths

  • Comfortable for the whole team every day (~10–40 users).
  • Backups no longer depend on anyone remembering; they are encrypted and stored with a second provider.
  • Outages are noticed in minutes, and someone is responsible for fixing them.
  • Professional company address.

Limits

  • Still one machine: updates cause under a minute of downtime, and recovery from a failure takes up to a few hours.
  • Data is in the EU, not in Israel. This is acceptable to most partners; check NDA wording.
  • Login is still username and password (no Microsoft/Google sign-on).
Best for: when the team relies on the app every day, and clients start asking “where is our data and how is it backed up?”

Option 3 · Expensive: high availability on AWS Tel Aviv

For enterprise clients

Amazon Web Services' Israel (Tel Aviv) region keeps all data inside Israel. The app runs on two servers in two separate data centers behind a load balancer and web firewall, with a managed PostgreSQL database that has a live standby copy. Staff sign in with their company Microsoft or Google account. This is a development project, not a settings change.

How it works

  1. The firewall filters attacks; the load balancer sends each request to a healthy container in either zone.
  2. Staff are redirected to Microsoft/Google to sign in; leavers lose access as soon as IT disables their company account.
  3. Both containers share one managed PostgreSQL database, which keeps a live standby in the other zone.
  4. Updates roll out one container at a time, so there is no downtime.
  5. Backups allow recovery to any minute in the retention window; documents and backup copies live in S3.

Strengths

  • Data stays in Israel. This is the strongest answer for NDA partners and enterprise contracts.
  • Survives a server or data-center failure, with no downtime for updates.
  • Company sign-on; access ends automatically when someone leaves.
  • Formal support with agreed response times, plus a security review.

Limits

  • Roughly 25–50× the monthly hosting cost of Option 1, plus the one-time project.
  • 1–2 months before go-live.
  • Needs code changes: move from SQLite to PostgreSQL, add Microsoft/Google sign-on, store documents in S3.
  • Cannot be run without the IT partner.
Note: the costs for this option are planning estimates based on typical AWS list prices and Israeli market rates. Get a quote from the AWS Pricing Calculator (region “Israel (Tel Aviv)”) and from an IT partner before deciding.
Best for: enterprise or government-linked clients, contracts that require data in Israel or an SLA, 40+ users, or several offices.
